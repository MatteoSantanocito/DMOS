# DMOS setup guide

How to build a testbed for DMOS and run the scheduler. DMOS runs on an
operator machine (the reference setup uses Windows with Git Bash and
PowerShell) and controls K ≥ 2 Kubernetes clusters joined by Cilium
ClusterMesh. Two ways to build the clusters:

| Path | Clusters | Status |
|---|---|---|
| **A — proxmox-k3s** (§2) | K3s clusters on Proxmox VE, created by [unict-cclab/proxmox-k3s](https://github.com/unict-cclab/proxmox-k3s) with Cilium, ClusterMesh and kube-prometheus-stack; DMOS add-ons by `scripts/setup-dmos-on-clusters.ps1` | the reference testbed (6 clusters) |
| **B — assisted bootstrap** (§3) | one single-node K3s cluster per Linux host, installed by the commands generated by `scripts/bootstrap-assisted.sh` | from the original three-node testbed; not re-validated on the current fleet (see the notes in §3) |

Both end with the same DMOS-side steps (§4–§6).

## 1. Operator machine

| Tool | Used for |
|---|---|
| Python 3.12 + `pip install -r requirements.txt` (virtualenv `venv/`) | DMOS, collector, analysis |
| `kubectl`, `helm` | cluster operations, add-on installs |
| `cilium` CLI | ClusterMesh checks |
| Git Bash (`bash`, `jq`, `ssh`, `scp`, `curl`) | harness and setup scripts |
| PowerShell 7 (`pwsh`) | `setup-dmos-on-clusters.ps1`, `reset_test.ps1` |
| k6 | on the load-generation VM (and optionally locally) |

```bash
git clone <repo-url> dmos && cd dmos
python -m venv venv
source venv/Scripts/activate        # Windows Git Bash; venv/bin/activate on Linux/macOS
pip install -r requirements.txt
```

## 2. Path A — proxmox-k3s (reference testbed)

### 2.1 Clusters

The proxmox-k3s (v0.3.0) file of the reference fleet is
[`config/proxmox-k3s-fleet.yaml.example`](../config/proxmox-k3s-fleet.yaml.example):
6 clusters, each with a control-plane node (2 vCPU / 4 GB) and a worker in
one of three tiers (HIGH 8 vCPU / 12 GB, MEDIUM 6 / 8, LOW 4 / 8), K3s
v1.36.0+k3s1 without flannel and kube-proxy, Cilium 1.19.4, kube-prometheus-stack,
non-overlapping Pod/Service CIDRs and the ClusterMesh ids. Copy it outside
the repository, replace the `<...>` placeholders (Proxmox API token,
addresses, Proxmox node names, VM template), then:

```bash
proxmox-k3s cluster create -c ms-cluster.yaml
proxmox-k3s cluster mesh   -c ms-cluster.yaml
```

The filled-in copy holds the Proxmox API token: keep it out of git. The
worker IPs you choose go also in `config/local.yaml` (§4).

The tool writes one kubeconfig per cluster (the reference layout is
`~/dmos-iac/kubeconfig-ms-cluster-NN`). kube-prometheus-stack is installed
in namespace `observability` with release name `prometheus-stack` and the
Prometheus NodePort **32090**.

### 2.2 DMOS add-ons

```powershell
pwsh scripts/setup-dmos-on-clusters.ps1 -KubeconfigDir "$HOME\dmos-iac"
```

On every cluster the script:

1. upgrades Cilium (`--reuse-values`) to export the Hubble `httpV2` metrics
   with the labels DMOS needs and to enable the Cilium Ingress controller on
   NodePort **30080**, then restarts the agents;
2. applies the Online Boutique release manifests (upstream
   `release/kubernetes-manifests.yaml`, branch `main`) in `online-boutique`;
3. applies the DMOS manifests: `00-namespace.yaml`, `cnp-frontend-l7.yaml`,
   `cnp-backends-l7.yaml`, `ingress-frontend-cilium.yaml`,
   `global-service-frontend.yaml`, `global-service-backends.yaml`,
   `hubble-servicemonitor-monitoring.yaml`. The frontend Service becomes a
   ClusterMesh global service with `affinity: none` (the data plane of the
   NCA paper: requests are spread over the frontend pods of all clusters);
   the four global backends use `affinity: local`
   ([CILIUM-CLUSTERMESH-NOTES.md](CILIUM-CLUSTERMESH-NOTES.md)).

Options: `-SkipCiliumUpgrade`, `-SkipOnlineBoutique`, `-SkipDmosManifests`,
`-IngressNodePort`, `-PrometheusReleaseLabel`.

Two notes on reproducibility:

- the Online Boutique manifests come from the upstream `main` branch, not a
  pinned release: record the image versions (they are in each run's
  `env_state_pre.json`) or pin the URL to a release tag;
- the manifests include the `loadgenerator` Deployment: keep it at 0
  replicas (the harness's reset does it, see [§6](#6-before-the-first-run)).

### 2.3 Workload hardening

```bash
bash experiments/apply_resource_hardening.sh     # memory/CPU limits, relaxed probes
bash experiments/apply_pod_lifecycle.sh          # preStop + termination grace (connection drain)
```

Re-run both after re-applying the Online Boutique manifests (they reset the
patched values). The resulting requests/limits are documented per service in
`config/services.yaml`.

Then continue with §4.

## 3. Path B — assisted bootstrap (generic hosts)

For N ≥ 2 Linux hosts (Ubuntu 22.04/24.04), one single-node K3s cluster per
host, all reachable from the operator machine.

### 3.1 Host prerequisites (manual)

- SSH key access from the operator machine (`ssh-copy-id`), passwordless
  sudo for the SSH user;
- open between the hosts: 6443/TCP (K3s API), 8472/UDP (VXLAN), 4240/TCP
  (Cilium health), 4244/TCP (Hubble), 32379/TCP (clustermesh-apiserver),
  30080/TCP (Ingress), the Prometheus NodePort, 9427/TCP (ping_exporter).

### 3.2 Generate configuration and commands

```bash
bash scripts/bootstrap-assisted.sh
```

It asks for the clusters (IP, region code, display name, carbon baseline,
netem delay), detects CPU and RAM over SSH, writes `config/local.yaml`,
renders `.cache/` (§4) and writes `bootstrap-commands.sh`: K3s install with
a distinct pod CIDR per cluster, Cilium with ClusterMesh, kube-prometheus-stack,
ping_exporter, Online Boutique and the DMOS manifests. Run that file
section by section, checking each step.

### 3.3 Known differences from the reference testbed

| Item | Bootstrap path | Reference (path A) | What to do |
|---|---|---|---|
| Cilium version | `--version 1.16.5` | 1.19.4 | prefer the newer version |
| Cilium Ingress controller | not in the rendered values | enabled by `setup-dmos-on-clusters.ps1` | add the `ingressController` block of [ingress-architecture.md §1](ingress-architecture.md#1-configuration) |
| Prometheus | kube-prometheus-stack installed with `config/prometheus-helm-values.yaml`, which is written for the standalone `prometheus` chart (NodePort 30090, `extraScrapeConfigs`) | kube-prometheus-stack from proxmox-k3s, NodePort 32090, ServiceMonitors | expose Prometheus on a NodePort and set `prometheus_port` per cluster in `local.yaml`; make sure the Hubble ServiceMonitor (`release: prometheus-stack`) matches your release |
| Workload hardening | not included | §2.3 | run the two scripts of §2.3 |

`bash scripts/validate-setup.sh` checks the result (kubeconfigs, Cilium,
ClusterMesh, Prometheus, ping_exporter, Hubble L7 metric, Ingress).

## 4. DMOS configuration

1. **`config/local.yaml`** (gitignored) — the testbed description: clusters
   (name, worker IP, kubeconfig, cores/memory, region and carbon zone,
   netem delay and interface), SSH user/key, optional Alertmanager webhook.
   Path B writes it; otherwise copy `config/local.yaml.example`. Every key is
   described in [configuration-reference.md §2](configuration-reference.md#2-localyaml--testbed).
   Carbon: the `region_code` (or its alias in `carbon.yaml →
   trace.zone_aliases`, e.g. `NO` → `NO-NO1`) must match a file
   `data/carbon_traces/<zone>_*hourly*.csv` to use the replayed traces. The
   traces are not distributed with the repository: download them with your
   own Electricity Maps access ([data/carbon_traces/README.md](../data/carbon_traces/README.md)),
   e.g. `python scripts/fetch_carbon_traces.py --zones DE FR PL US-MIDA-PJM SG NO-NO1 --year 2025`
   ([configuration-reference.md §5](configuration-reference.md#5-carbonyaml--carbon-intensity)).
   Quote `region: "NO"` and `region_code: "NO"`: a bare NO is a YAML boolean.
2. **Render the runtime files** (after every change of `local.yaml`):

   ```bash
   bash scripts/render-runtime-files.sh
   ```

   It writes `.cache/test-env.json` / `.cache/test-env.sh` (used by k6, the
   collector and the harness) and the Cilium and ping_exporter Helm values.
3. **Emulated geography and RTT probes:**

   ```bash
   bash scripts/setup-netem-and-ping.sh            # netem on the workers + ping_exporter
   bash scripts/setup-netem-and-ping.sh verify
   ```

   netem is lost at every VM reboot: re-apply it with `netem-only` (the run
   harness refuses to start without it).
4. **Check the configuration offline:**

   ```bash
   DMOS_SCORE_MODEL=nca python -m src.dmos_main --dump-config-only /tmp/cfg.json
   ```

   prints the effective configuration summary without contacting the
   clusters.

## 5. Running DMOS

```bash
python -m src.dmos_main                         # legacy profile (weights.yaml → active)
DMOS_SCORE_MODEL=nca python -m src.dmos_main    # NCA 2026 configuration
python -m src.dmos_main --no-scheduling         # Level 2 only (uniform N/K)
```

At start-up the log shows the clusters, the score in use
(`Score model 'nca' [warm] demand_mode=gate: …`), the effective-config summary
with its `config_id`, and then one cycle every 30 s; for the first 120 s
`⏳ Grace period …` (no scaling). Endpoints: `http://localhost:9090/metrics`,
`http://localhost:8081/health`, `http://localhost:8081/config`. Run from the
repository root (the configuration is read from `./config`).

## 6. Before the first run

```bash
bash experiments/preflight_runs.sh          # Ingress, pods, netem, ClusterMesh, Hubble
bash experiments/preflight_runs.sh --fix    # also re-applies netem
```

- Online Boutique `loadgenerator`: it must not run during experiments (its
  internal traffic reaches the frontend without passing through k6). The
  harness's reset (`scripts/reset_test.ps1`, `experiments/clean_reset.sh`)
  scales all Deployments to 1 and then the `loadgenerator` to 0, and every
  cell refuses to start while it has replicas.
- Frontend data plane: `preflight_runs.sh` reports the frontend's affinity
  and how many backends its Service has in the Cilium datapath; with the
  paper configuration (`affinity: none`) the pool holds the frontend pods of
  all six clusters.
- The load-generation VM must have k6 installed and the SSH key of
  `local.yaml`; export `DMOS_K6_REMOTE=ubuntu@<k6-vm>`.

Then follow [../experiments/RUNBOOK.md](../experiments/RUNBOOK.md).

## 7. Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `Config file not found: config/local.yaml` | create it (§4) |
| `.cache/test-env.json not found` | `bash scripts/render-runtime-files.sh` |
| DMOS logs `Prometheus not reachable at …` / all traffic 0 | wrong `ip` or `prometheus_port`; the worker IP must expose the NodePort |
| `hubble_http_requests_total` missing | [cilium-hubble-l7-visibility.md §4](cilium-hubble-l7-visibility.md#4-pitfalls-and-fixes) |
| `cilium clustermesh status` not connected | open 32379/TCP between the clusters; check the clustermesh-apiserver |
| `ping_rtt_mean_seconds` absent or NaN | the pods cannot reach the peer IPs; check with a busybox `ping` from the cluster |
| a run is aborted with "netem" | `bash scripts/setup-netem-and-ping.sh netem-only` |
| cross-cluster pod traffic times out | VXLAN MTU: set `mtu: 1450` in the Cilium values |

More in [troubleshooting.md](troubleshooting.md).
